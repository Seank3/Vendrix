# Deploying Vendrix

This guide covers the recommended hosting split for Vendrix, plus the alternatives you asked about.

## Where each piece should live

| Piece of Vendrix | Render | Netlify | Vercel | Supabase |
|---|---|---|---|---|
| Django API (`vendrix/`) | ✅ **best** | ❌ (functions only) | ⚠️ serverless, no workers | ❌ (not a Django host) |
| Celery worker (async sync, event bus) | ✅ **best** | ❌ | ❌ | ❌ |
| Redis (broker/cache) | ✅ managed | ❌ | ✅ Upstash add-on | ❌ |
| PostgreSQL | ✅ managed | ❌ | ✅ Neon add-on | ✅ **best-in-class** |
| React console (`frontend/`) | ⚠️ possible | ✅ | ✅ | ❌ |

**Recommended stack (Option A):** `Render (API + Celery worker + Postgres + Redis)` + `Netlify (frontend)`.

**Variants (Option B):** swap Render's Postgres for **Supabase** (better dashboard, storage for future product images).
**Option C:** swap Netlify for **Vercel** — keep `frontend/vercel.json`, set root directory to `frontend`.

## Option A — Render (backend) + Netlify (frontend)

### 1. Render — the Django API

1. Push this repo to GitHub. In Render: **New → Blueprint → select the repo** and apply `render.yaml`.
   It creates four resources:
   - `vendrix-api` — web service (Gunicorn), runs `migrate` on start
   - `vendrix-worker` — Celery worker (processes sync jobs & domain events)
   - `vendrix-redis` — Redis (broker + cache)
   - `vendrix-db` — PostgreSQL
2. **Set two env vars manually** on `vendrix-api` (blueprint marks them `sync: false`):
   - `CREDENTIALS_ENCRYPTION_KEY` →
     ```
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
   - `CORS_ALLOWED_ORIGINS` → your frontend origin, e.g. `https://vendrix-console.netlify.app`
3. Deploy. The health check (`GET /health/`) returns `{"status":"ok"}`.
4. **First login** (no shell needed) — register an organization via the API:
   ```
   curl -X POST https://vendrix-api.onrender.com/api/v1/auth/register/ \
     -H "Content-Type: application/json" \
     -d '{"organization_name":"Acme","organization_slug":"acme","admin_email":"boss@acme.com","admin_password":"Str0ngPass!"}'
   ```
   Or run the seeder from the Render shell (or any machine with the repo):
   ```
   DJANGO_SETTINGS_MODULE=vendrix.settings.production python scripts/run_seed_admin.py
   ```
5. Optional: point your own domain at `vendrix-api.onrender.com`.

### 2. Netlify — the console

1. In Netlify: **Add new site → Import an existing project → GitHub**.
2. Build settings are already in `netlify.toml` (base `frontend/`, `npm run build`, publish `dist`).
3. Add environment variable in Netlify UI (Site → Settings → Environment):
   ```
   VITE_API_BASE_URL = https://vendrix-api.onrender.com/api/v1
   ```
   *(The SPA fallback rewrite is already configured.)*
4. Deploy. The SPA talks to the API cross-origin using your JWT/API keys — CORS was allowed in step A.2.

> **No-env alternative:** Netlify can *proxy* `/api/*` to Render via a 200-rewrite, which avoids CORS entirely:
> ```toml
> [[redirects]]
>   from = "/api/*"
>   to = "https://vendrix-api.onrender.com/api/:splat"
>   status = 200
> ```
> (then leave `VITE_API_BASE_URL` unset). The CORS approach above is the more standard one.

## Option B — Supabase as the database

1. Create a Supabase project (free tier: 500 MB — pauses after 7 days of inactivity).
2. Copy the **connection string**: `Settings → Database → Connection string (URI)`, `Session pooler` (port 5432/6543).
3. In Render, set on **both** `vendrix-api` and `vendrix-worker`:
   ```
   DATABASE_URL = postgresql://postgres:YOUR_PASSWORD@db.xxxx.supabase.co:5432/postgres?sslmode=require
   ```
   (Django reads `DATABASE_URL` automatically — see `vendrix/settings/base.py`.)
4. Delete the `vendrix-db` block from `render.yaml` (or just ignore it) and redeploy.
5. Run migrations automatically happens on start (`python manage.py migrate --noinput`).

Why you'd pick Supabase: visual DB editor/SQL console, row-level security if you later add direct app access, instant storage buckets (handy if product image uploads arrive), generous free tier.

## Option C — Vercel for the frontend

1. Import the repo in Vercel, set **Root Directory → `frontend`**.
2. `frontend/vercel.json` already handles the SPA fallback rewrite.
3. Add env var `VITE_API_BASE_URL = https://vendrix-api.onrender.com/api/v1` and deploy.
4. Don't try to host Django on Vercel: it would run as serverless functions with no Celery worker, no long-lived Redis connection — sync jobs and the event bus would silently degrade.

## Environment variables (production)

| Var | Where | Required | Notes |
|---|---|---|---|
| `DJANGO_SETTINGS_MODULE` | Render | ✅ | `vendrix.settings.production` |
| `SECRET_KEY` | Render | ✅ | auto-generated by blueprint |
| `CREDENTIALS_ENCRYPTION_KEY` | Render | ✅ | **Fernet key** — see above; must never change |
| `ALLOWED_HOSTS` | Render | ✅ | `.onrender.com` (+ your domain) |
| `CORS_ALLOWED_ORIGINS` | Render | ✅ | exact frontend origin(s) |
| `DATABASE_URL` | Render | ✅ | Render/Supabase/Railway connection string |
| `REDIS_URL` | Render | ✅ | wired from `vendrix-redis` |
| `VENDRIX_EVENT_BUS_BACKEND` | Render | ✅ | `celery` (prod); dev uses `sync` |
| `CSRF_TRUSTED_ORIGINS` | — | admin login | e.g. `https://vendrix-api.onrender.com` |
| `VITE_API_BASE_URL` | Netlify/Vercel | ✅ | build-time; no trailing slash |

## Free-tier reality check (what expires / spins down)

| Resource | Free limit | Gotcha |
|---|---|---|
| Render web/worker (free) | 750 h/month | **Spins down after 15 min idle** → ~50 s cold start on first request |
| Render Postgres (free) | 1 GB | **Deleted after 30 days** — upgrade to `basic-256mb` (~$7/mo) for real production |
| Render Redis (free) | 25 MB | fine for a queue; upgrade for prod |
| Supabase (free) | 2 projects / 500 MB | **Pauses after 7 days of inactivity** — click Restore in dashboard |
| Netlify (free) | 100 GB/mo bandwidth | static hosting, no expiry; fine |
| Vercel (hobby) | 100 GB/mo | fine for the SPA |

**Cheapest always-on production setup:** Render `starter` web ($7) + `basic-256mb` Postgres ($7) + free Redis + Netlify free = **~$14/mo**.

## Continuous integration & deployment (GitHub Actions)

`.github/workflows/` contains:

| Workflow | When | What it does |
|---|---|---|
| `ci.yml` | every push / PR to `main` | Python 3.12 + Node 20 matrix: `manage.py check`, migration-drift check, **production-settings import + fail-fast guard test**, fresh-DB `migrate` + seeder, and a clean `vite build` |
| `deploy.yml` | push to `main` | **Only runs jobs whose secrets exist.** Netlify build+deploy; Render deploy-hook trigger |

**Secrets to add** (GitHub → Settings → Secrets and variables → Actions):

| Secret | Needed for | How to get it |
|---|---|---|
| `NETLIFY_AUTH_TOKEN` | Netlify deploy job | Netlify → User settings → Applications → Personal access tokens |
| `NETLIFY_SITE_ID` | Netlify deploy job | Site → Site configuration → Site details → Site ID |
| `VITE_API_BASE_URL` | Netlify deploy job (optional) | defaults to `https://vendrix-api.onrender.com/api/v1` |
| `RENDER_DEPLOY_HOOK_URL` | Render job (optional) | Render → Service → Settings → Deploy hooks → create hook |

Render Blueprint **auto-deploys on every push** once the repo is connected — the deploy hook is only a backup for services with `autoDeploy` disabled.

## What was added to the repo

- `vendrix/settings/production.py` — env-driven prod settings (fails fast on missing secrets)
- `render.yaml` — Render blueprint (API + worker + Redis + Postgres)
- `netlify.toml` — Netlify build + SPA fallback
- `frontend/vercel.json` — Vercel SPA rewrites
- `health/` endpoint (`GET /health/`) — liveness probe
- `DATABASE_URL` + `DB_SSLMODE` support, Whitenoise (serves admin static files without nginx)
- `scripts/run_seed_admin.py` — works on a fresh hosted DB (creates the org too)
- `VITE_API_BASE_URL` support in `frontend/src/services/api.js`
- `.github/workflows/ci.yml` + `.github/workflows/deploy.yml` — CI and guarded deploys
